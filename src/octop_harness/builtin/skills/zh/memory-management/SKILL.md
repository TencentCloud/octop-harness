# 记忆管理

harness 提供一组记忆文件，代理在**每次**对话开始时都会读取。使用它们来存储应该在多轮、多线程甚至进程重启之间存活的持久上下文。

## 文件说明

| 文件 | 用途 | 何时更新... |
|------|---------|----------------|
| `USER.md` | 关于人类和代理的稳定信息：姓名、角色、偏好的语气、语言、行为规则。 | 用户分享个人信息、表达偏好或纠正你的风格时。 |
| `MEMORY.md` | 项目级长期笔记：决策、约束、经验教训、环境配置。 | 某一轮产生了下次还需要的事实时。 |
| `AGENTS.md` | 项目约定（构建命令、代码风格、仓库布局）。 | 用户阐明项目应该如何被处理时。 |

短暂的当日上下文（单一情绪、经过的事件、此刻的问题）**不**属于这些文件中的任何一个——将它们留在对话中。只有当下次仍需要某个事实时，才将其提升到记忆文件中。

## 何时更新记忆

- **可提升的信号**：用户说"记住……"、"从今以后……"、纠正你的风格，或分享你否则会重复询问的上下文信息。
- **环境信号**：你注意到在多轮对话中你一直在重复推导同一个事实。将其提升到适当的记忆文件中。

**不要**将每次聊天都转储到记忆中。顶层文件在每一轮都会被读取——臃肿会消耗未来每次对话的 token。只有当事实是持久的时候才提升到 `USER.md`/`MEMORY.md`；短暂上下文属于对话，不属于记忆文件。

## 如何更新

1. **先 `read_file`** 目标记忆文件。你是在修订，不是在重新创建。
2. **小改动用 `edit_file`**：在正确的部分下添加要点。当只需要在末尾添加新行时，使用 **`append_file`**。
3. 保持条目简洁：每个事实 1-2 行。使用要点，不使用段落。
4. 按部分分组（例如 `## 编码风格`、`## 用户偏好`）。在添加之前先创建部分（如果尚不存在）。
5. **永远不要对任何记忆文件使用 `write_file`**：它会覆盖所有内容。
6. 更新后，简要告诉用户你保存了记忆以及保存位置，以便他们可以纠正误解。

## 什么不应该放入记忆

- 秘密/API 密钥/凭证。如果被要求，拒绝。
- 仅限会话的上下文（用户*当前*的问题）。那属于聊天历史；记忆是用于应该持久化的东西。
- 大量逐字记录的文字记录。总结。

## 冲突处理

如果新指令与现有记忆矛盾，**删除或更新旧行**而不是追加。记忆中有两个矛盾的事实会在下次混淆你。当有疑问时，询问用户保留哪一个。
